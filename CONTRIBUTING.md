# Contributing to openDox Client

Thank you for considering a contribution! The openDox Client is the desktop part of
[openDox](https://github.com/daemolition/openDox): a small always-on-top overlay for dictating
and inserting medical text. For an overview of what it does and how it is built, start with
[`docs/opendox-client.md`](docs/opendox-client.md).

## Code of Conduct

This project and everyone participating in it is governed by our
[Code of Conduct](CODE_OF_CONDUCT.md). By participating, you are expected to uphold it.

## How Can I Contribute?

### Reporting Bugs

Before creating a bug report, please check the existing issues. Include:

- **A clear and descriptive title**
- **Exact steps to reproduce** the problem, and what you expected instead
- **Your environment:** operating system and version, client version, server version
  (`/api/version`), how it was installed (MSI, setup.exe, macOS app, built from source), the
  program that should receive the text (Citrix/RDP?), the dictation microphone model if any
- **Log output** — start the client with `--debug` — **redacted**

> **Never include real patient data, dictated text, tokens or window titles** in issues,
> screenshots or logs. openDox is not a certified medical device.

### Suggesting Enhancements

Open an issue with the problem you want to solve, a proposed solution and alternatives you
considered. For larger changes please discuss before writing code.

### Pull Requests

1. Fork the repository
2. Create a branch from `master`: `git checkout -b feature/your-feature-name`
3. Make your changes
4. Run formatting, vet and tests (see below)
5. Commit with a clear message (see [Commit Messages](#commit-messages))
6. Push to your fork and open a Pull Request — the template has a checklist

## Development Setup

### Prerequisites

Go (see `go` in `go.mod`), Node.js 22+, the [Wails v2 CLI](https://wails.io) matching the version
in `go.mod`, and the platform libraries listed in the [README](README.md#voraussetzungen)
(Linux: `webkit2gtk-4.1`, GTK 3, `libusb-1.0` and X11 headers for the dictation-mic and hotkey code).

### Run it

```bash
cd frontend && npm install && cd ..
wails dev
```

More ways to start it (including `go run -tags dev,webkit2_41 .`) are in the
[README](README.md#entwicklung). The client needs an openDox server; without a `settings.json` it
uses `http://localhost:10000`.

## Project conventions

- **Go does OS work, React does the rest.** `App` (`app.go`) is the only object bound to the
  frontend; new OS-level or token-attaching backend calls become methods on it, pure browser REST
  stays in the frontend. See [`.agents/AGENTS.md`](.agents/AGENTS.md) for the architecture and the
  gotchas (closure refs for hotkey handlers, why `robotgo.KeyTap` is not used on macOS, ...).
- **OS-specific code:** use `//go:build` files with a real implementation plus no-op stubs
  (`foo_windows.go` / `foo_darwin.go` / `foo_other.go`), not `runtime.GOOS` checks.
- **Testable logic without OS or Wails** goes into `internal/` (see `internal/clientpolicy`).
- **Do not hand-edit `frontend/wailsjs/`** — it is regenerated by `wails dev` / `wails build`.
- **Never log or persist** the foreground window title, tokens, dictated text or audio. Do not add
  an automatic clipboard copy after processing — text reaches the target only via the explicit
  accept step.
- **No new outbound connections** besides the configured server. If you need one, it needs an
  entry in [`docs/data-mapping.md`](docs/data-mapping.md) and a discussion first.
- Keep the **"Kein Medizinprodukt" disclaimer** and the accept-and-insert step intact.
- UI strings and comments are largely German (German-market product) — match the surrounding language.

## Code Style

```bash
gofmt -l $(git ls-files '*.go' | grep -v '^third_party/')   # must print nothing
go vet ./...
cd frontend && npm run typecheck        # tsc --noEmit; `npm run build` does not type-check
```

Frontend: TypeScript, plain per-component `.css` (no CSS framework). `color-scheme: dark` in
`style.css` is load-bearing for native form controls on WebKitGTK — do not remove it.

## Testing

```bash
xvfb-run -a go test ./...                       # package main imports hotkey, which needs an X11 display
GOOS=windows go vet ./internal/...              # Windows-only packages cannot be built here (robotgo/cgo)
```

There is no frontend test setup. Behavior on real Windows/macOS (clipboard history, hotkeys,
paste, WebView permissions, dictation microphones) has to be checked by hand — please say in the
PR which platforms you tried.

## Licensing and headers

openDox Client is **AGPL-3.0-or-later** and the repository is [REUSE](https://reuse.software)
compliant.

- New source files (`.go`, `.ts`/`.tsx`, `.py`) get the AGPL header — copy it from a neighbouring
  file (Go uses `//` line comments, so it does not break `//go:build` constraints; the constraint
  may only be preceded by blank lines and other line comments).
- Add the SPDX short tags with `python3 scripts/add_spdx_headers.py` and verify with `reuse lint`
  (`pip install reuse`). Non-source files are covered in bulk by `REUSE.toml`.
- Changing dependencies? Regenerate the notices and check compatibility:

  ```bash
  python3 scripts/check_licenses.py --write-notices
  ```

  Only AGPL-compatible licenses are allowed; the script lists anything it cannot classify.
- `third_party/` holds patched copies of `hid` and `hotkey` (see `replace` in `go.mod`). Keep their
  upstream license notices intact.

## Documentation

- Update [`docs/data-mapping.md`](docs/data-mapping.md) and [`SECURITY.md`](SECURITY.md) when
  data handling, network traffic, logging, clipboard behavior or local storage changes.
- Update [`.agents/AGENTS.md`](.agents/AGENTS.md) when commands, architecture or gotchas change.
- Add an entry under `## [Unreleased]` in [`CHANGELOG.md`](CHANGELOG.md) for user-visible changes.

## Commit Messages

Use conventional commit format:

```
<type>(<scope>): <subject>

<body>

<footer>
```

**Types:** `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`.

```
fix(insert): wait for modifier keys to be released before pasting

Ctrl+Alt from the global hotkey was still down when Ctrl+V was sent,
leaving the text in the clipboard on X11.
```

## Releases

Releases are cut by a maintainer. The single canonical version is `info.productVersion` in
`wails.json` (embedded into the Windows resource and the macOS plist, used for the MSI).

1. Make sure `CHANGELOG.md` has the entries under `## [Unreleased]`.
2. Bump version, move the changelog section, commit and tag:

   ```bash
   python3 scripts/bump_version.py minor --commit     # or patch / major / X.Y.Z
   git push origin master --follow-tags
   ```

   `.github/workflows/release.yml` checks that the tag matches `wails.json`, and publishes the
   changelog section as the GitHub Release notes.
3. Build the **signed** installers locally and attach them under their fixed names:

   ```bash
   ./build-windows-msi.sh && ./compile.sh     # Linux: MSI + NSIS setup
   ./build-macos.sh                           # on a Mac
   scripts/release.sh X.Y.Z                   # needs the gh CLI
   ```

   The file names are fixed because the openDox server links to
   `releases/latest/download/<name>` from its admin UI — keep them in sync with the server's
   `_CLIENT_DOWNLOAD_FILES`. A new client release is therefore available to all servers without a
   server update.

Client features that need a newer server (e.g. the client policy endpoint) are noted in the
changelog entry.

## Pull Request Process

1. **Update documentation** for any changed functionality
2. **Add tests** where the logic is testable without OS/Wails
3. **Ensure formatting, vet and tests pass** (see above) — CI runs them on every push and PR
4. **Run `reuse lint`** and, if dependencies changed, `scripts/check_licenses.py`
5. **Update `CHANGELOG.md`**
6. **Link related issues** in the PR description

## Review Criteria

Maintainers review for:

- **Security & privacy:** no new data leaves the machine, nothing sensitive is logged or persisted
- **Functionality:** works as intended on the platforms stated in the PR
- **Tests:** logic that can be tested is tested
- **Documentation:** data-mapping, SECURITY, AGENTS and CHANGELOG are up to date
- **Style:** follows the conventions above

## Getting Help

- **General questions and bug reports:** open an issue on GitHub
- **Security concerns:** see [SECURITY.md](SECURITY.md) — do not open a public issue
